# P13 Agentic AI Project — Typed Read-Only Tool System with Ollama and Interactive UI

You are a senior Python/AI systems engineer.

Build a complete, production-quality educational project implementing the following assignment:

> **P13 · A typed tool set and a manifest**
>
> Build three read-only tools with `extra="forbid"` input models, pattern-constrained identifiers, row limits with truncation flags, and a decorator performing five checks at import. Generate a manifest from the registry and make CI fail when the committed manifest differs from the generated manifest.
>
> Completion requirements:
>
> * A tool without a description cannot be registered.
> * A tool without a row limit cannot be registered.
> * Malformed arguments must never reach the handler.
> * Identifier regexes must use `[0-9]`, NOT `\d`.
> * The project must demonstrate the complete flow through an Agentic AI interface.
>
> The referenced implementation concepts are from Read-Only Build Guide §2.1, §2.6 and Day 4 · Implementation Guide — Adapters.

---

# 7. PYDANTIC INPUT MODELS

Every tool must have a dedicated Pydantic v2 input model.

Every model MUST use:

```python
model_config = ConfigDict(extra="forbid")
```

Example concept:

```python
class ProductInput(BaseModel):
    model_config = ConfigDict(extra="forbid")

    product_id: str = Field(
        pattern=r"^P[0-9]+$"
    )
```

Do not use:

```python
r"^P\d+$"
```

because this project explicitly requires ASCII digits.

Use:

```python
[0-9]
```

for numeric identifier patterns.

Test Unicode digits explicitly.

For example:

```text
P123      -> valid
P१२३     -> invalid
P１２３    -> invalid
Pabc      -> invalid
```

# 8. LIMIT VALIDATION

Use Pydantic to validate the requested row limit.

Example:

```python
limit: int = Field(
    default=20,
    ge=1,
    le=100
)
```

The exact maximum can be configured centrally.

Never allow the LLM to request an unlimited result set.

The server must enforce the limit even if the LLM requests:

```text
limit = 1000000
```

# 9. TRUNCATION

Every row-returning tool must clearly communicate whether the result was truncated.

Return a structure conceptually similar to:

```json
{
  "rows": [],
  "count": 20,
  "truncated": true
}
```

Rules:

* `truncated=false` if all matching rows were returned.
* `truncated=true` if additional matching rows existed beyond the maximum returned amount.

Do not simply slice the data and hide the fact that more data existed.

The UI must visibly show:

* Returned rows
* Maximum rows
* Truncated status

Use a clear warning when:

```text
truncated = true
```

```python
@read_tool(
    name="get_product",
    description="Retrieve product information by product ID.",
    row_limit=1
)

    ...
```

The decorator must validate the tool at IMPORT/REGISTRATION time.

Do not wait until the tool is called.

# 11. FIVE REGISTRATION CHECKS

Implement exactly five explicit registration-time checks.

Organize them clearly in code.

The five checks should cover:

1. Tool has a valid non-empty description.
2. Tool declares a valid row limit.
3. Tool has a valid typed Pydantic input model.
4. Tool has a valid callable handler/signature.
5. Tool conforms to the read-only tool contract and can be safely registered.

If the referenced course material specifies more precise definitions for the five checks, follow the course material exactly.

Each failed check must produce a clear developer-facing error.

Examples:

```text
ToolRegistrationError:
Tool 'get_products' cannot be registered:
missing description
```

and:

```text
ToolRegistrationError:
Tool 'get_orders' cannot be registered:
missing row_limit
```

```python
TOOL_REGISTRY = {}
```

# 13. MALFORMED INPUT MUST NEVER REACH THE HANDLER

This is a mandatory security invariant.

The execution flow must be:

```text
LLM
 ↓
Tool call
 ↓
Parse arguments
 ↓
Pydantic validation
 ↓
Business rules
 ↓
Handler
```

NOT:

```text
LLM
 ↓
Handler
 ↓
Validation
```

Create tests proving this.

Use a spy/mock handler.

For malformed arguments:

```text
handler_called == False
```

must be asserted.

Test at least:

1. Missing required field
2. Wrong type
3. Invalid identifier
4. Unicode digit identifier
5. Extra unknown field
6. Invalid limit
7. Excessive limit

# 14. READ-ONLY GUARANTEE

The three tools must be read-only.

Do not expose:

* insert
* update
* delete
* drop
* alter
* truncate
* arbitrary SQL execution

Do not allow the LLM to submit arbitrary SQL.

Handlers should use predefined parameterized queries.

For example:

```sql
SELECT ...
FROM products
WHERE product_id = ?
```

Never construct SQL by string concatenation using LLM-generated values.

```json
      "row_limit": 1,

```

Sort tools deterministically so the manifest does not change because of dictionary ordering.

Generate stable JSON formatting.

# 16. MANIFEST DRIFT DETECTION

Implement:

```bash
make manifest
```

and/or an equivalent command.

The command must generate the manifest and verify that the committed manifest matches the generated manifest.

If the committed file differs:

```text
FAIL
```

If identical:

```text
PASS
```

CI must fail on mismatch.

Do not silently overwrite the committed manifest during CI.

A useful pattern is:

```bash
python scripts/generate_manifest.py --check
```

where:

* normal mode generates the file
* `--check` compares generated output with the committed file

# 18. OLLAMA AGENT

Build an agent layer using Ollama.

The agent should:

1. Accept natural-language user requests.
2. Provide the three registered tools to the model.
3. Allow the model to decide which tool to call.
4. Extract tool arguments.
5. Pass them into the Pydantic validation layer.
6. Execute only validated tools.
7. Return tool results to the model.
8. Let the model produce a natural-language answer.

The LLM should NEVER directly call the database.

The architecture must remain:

```text
User
 ↓
LLM
 ↓
Tool call
 ↓
Registry
 ↓
Validation
 ↓
Handler
 ↓
Database
 ↓
Tool result
 ↓
LLM
 ↓
User
```
